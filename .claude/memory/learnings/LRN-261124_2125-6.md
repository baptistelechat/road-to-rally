# LRN-261124_2125-6 — Nouveau MeshData dans StageData : le traiter dans validEntry

**Pattern observé** : IndexedDB rend les maillages en `Float32Array`/`Uint32Array`, alors que `parseStage` exige des tableaux simples (`numbers` vérifie `Array.isArray`). `validEntry` (`src/game/stageCache.ts`) retire donc le terrain avant `parseStage` et le remet ensuite. Un maillage ajouté ailleurs dans `StageData` (la roche des tunnels, `tunnels[].roof`) fait échouer la relecture en silence (`console.warn`), et l'écran affiche « Cette spéciale n'est plus disponible ».

**Contexte** : premier import d'un GPX avec tunnel, juste après le paquet 1.

**Application future** : tout nouveau `MeshData` dans `StageData` demande trois choses : `parseMesh` dans le codec, `meshToJson` dans `stageToJson`, et un retrait puis une remise dans `validEntry`, avec le contrôle `typedMesh`.

**Mise à jour du 2026-11-28** : `validEntry` recopiait aussi les champs du tunnel un par un (`from`, `to`, `halfWidth`) pour retirer la roche, et a perdu le nouveau champ `portal`, même écran « plus disponible ». Retirer seulement le maillage et étaler le reste (`{ ...tunnel, roof: undefined }`) : un champ ajouté plus tard passe tout seul ([BLK-261128_1831-6](../blockers/BLK-261128_1831-6.md)).
