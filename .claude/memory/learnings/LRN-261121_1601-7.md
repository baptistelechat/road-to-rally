# LRN-261121_1601-7 — Un check qui échoue tôt masque tous les suivants

**Pattern observé** : `stage.check.ts` échouait à `checkStartLine` (glissement de 0,9 mm) parce qu'il testait encore l'ancien départ (« immobile jusqu'au premier gaz ») alors que le décompte de 3 s le libère au GO, pile au 180ᵉ pas du test. Comme ce check s'exécutait en premier, toutes les vérifications suivantes de `stage` (`road`, `mountain`) ne tournaient plus depuis le 4/11, sans que personne le voie. Pour savoir si un échec vient de ses changements, relancer le check sur le code d'avant avec `git stash push -- src` puis `git stash pop` : même valeur, donc pas une régression.

**Contexte** : Session du 21/11, premier `check:determinism stage` depuis l'epic 4.

**Application future** : Quand un comportement change (décompte, départ, règle de jeu), chercher les checks qui testent l'ancien comportement (`grep` sur le nom de la fonction ou de la constante) et les mettre à jour dans le même commit. Devant un échec inattendu, comparer au code d'avant par `git stash` avant de chercher un bug.

**Ajout (2026-11-22)** : Un changement de règle peut aussi faire boucler un check sans fin : `checkActiveNotes` attendait la phrase du virage de départ de `mountain`, que la nouvelle règle ne dit plus (`while (feed(...)?.index !== index)`). Partager la règle dans le check (`firstHeard`) plutôt que de corriger chaque attente. Autre cas : le bot (`src/sim/bot.ts`) suit l'axe sans contourner les chicanes, donc tout check qui fait rouler le bot sur `road` échoue depuis l'ajout de ses chicanes ; `pace-note-cue` le fait rouler sans elles (`obstacles: undefined`).
