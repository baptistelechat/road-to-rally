# Story 1.3 : Couche d'entrées clavier et manette

**Statut : validé**

## Objectif

Clavier et manette produisent la même structure, une fois par pas de simulation. La simulation ne sait pas d'où vient l'entrée.

```ts
interface CarInput {
  steer: number; // -1 à 1
  throttle: number; // 0 à 1
  brake: number; // 0 à 1
  handbrake: boolean;
}
```

## À faire

- Clavier : flèches et ZQSD (AZERTY), espace pour le frein à main, `R` pour la remise en piste. Utiliser `event.code` pour rester indépendant de la disposition, en affichant les touches correspondantes.
- Le clavier est binaire : monter et descendre `steer`, `throttle` et `brake` progressivement, avec un retour au centre plus rapide que l'aller.
- Manette : Gamepad API, standard mapping, zone morte sur le stick, gâchettes analogiques.
- La manette prend le relais dès qu'elle bouge, sans réglage.
- Enregistrer les entrées par pas dans un tableau : `recordInputs` sera réutilisé par le fantôme et le rejeu.
- Panneau de debug qui affiche les quatre valeurs en direct.

## Critères d'acceptation

- [x] Les deux périphériques fonctionnent sans redémarrage, branchement à chaud compris.
- [x] Sur un clavier AZERTY comme QWERTY, la position physique des touches reste la même.
- [x] Perdre le focus de la fenêtre relâche toutes les touches.
- [x] Vérification dans `pnpm check:determinism` : la lecture d'un enregistrement redonne exactement les mêmes entrées, pas par pas.

## Pièges

- La Gamepad API se lit en polling : la lire dans la boucle de simulation, pas sur un événement.
- La manette n'apparaît souvent qu'après une première pression de bouton : prévoir un message.
- L'échantillonnage clavier doit se faire au pas de simulation, jamais à l'image, sinon le rejeu dérive.
